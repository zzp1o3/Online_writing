# AI 长篇小说创作流水线 · 设计文档

> 状态：需求访谈已完成，进入方案设计阶段
> 基础：基于 InkOS v1.7.2 二次开发（改版，复用原版 Studio Web UI）
> 定位：自用工作流产品，输入设定，输出一整本长篇小说

---

## 1. 目标与验收

- 输入：世界观 + 主角 + 简介（一份 brief）
- 输出：完整长篇小说（80 万 ~ 200 万字网文），章节化，可导出
- 验收标准：
  - 从头读到尾，主线不崩，角色设定完整，达到爽文节奏
  - 用户逐章人工阅读验收（人肉主编），可要求重新生成 / 局部重启
- 自动化边界：AI 完成设定、架构、分支、写作、审判、整理全流程；用户在关键节点把关

## 2. 已确认决策（需求基线）

| 维度 | 决策 |
| --- | --- |
| 开发方式 | InkOS 二次开发，直接改版，复用原版 UI，不先跑通原版 |
| 输入 | 世界观 + 主角 + 简介，AI 生成全部设定（用户可修改） |
| 输出 | 一整本长篇小说，逐章产出、逐章验收 |
| 验收方式 | 每章人工阅读：通过 / 整章重来 / 局部重启（划范围 + 指令） |
| AI 审判 | 每章写完后自动审计 + 去 AI 味 + 重写循环，通过后再交人工 |
| 记忆 | 三层记忆 + 向量 RAG；embedding API 由用户自配（如硅基流动免费 embedding） |
| 伏笔管理 | 守护 Agent 每章开头检查：该铺的伏笔是否铺、该收的线是否丢，标记提醒 |
| 卡片 | 结构化卡片（角色 / 地点 / 势力 / 物品），界面美观；仅守护 Agent 与用户可改 |
| 分支图谱 | 主线 1 条，分支最多 N 条，每条必须汇入灰度主线节点；AI 生成并更新，AI 与用户都有权砍分支 |
| 戏份控制 | 支线角色戏份超过主角判定为崩，需监控与裁剪 |
| 砍分支 | 分支被砍时，受影响章节回滚重写 |
| 写入生效 | 用户可选：直接写入 或 点头后才生效（逐项审批） |
| 模型 | 每个 Agent 单独配置模型（service / model / baseURL / key），由用户决定 |
| 局部重启 | 用户划定范围 + 写入描述，Agent 从全局视角重写但聚焦该段落 |
| Agent 能力 | Agent 可挂载 skills（如去除 AI 味 skill） |
| 成本 | 不考虑 API 成本，怎么好怎么来 |
| 生成节奏 | 一章一章写，不预写缓冲（可保留 AI 预写建议） |
| 量化规则 | 有量化规则但可变，不写死，可被用户与守护 Agent 调整 |

## 3. 总体架构

见架构图：`docs/整体架构.drawio`（或导出 PNG）。

分层（自顶向下）：

1. 用户层（人肉主编）：输入设定、逐章验收、砍分支、改卡片、局部重启指令
2. 工作台层（InkOS Studio 改版，Web）：分支图谱视图、章节审批面板、卡片视图、设定编辑器、流水线控制台、模型/嵌入配置
3. 编排层（Core）：Scheduler、Runner / 审批状态机、写入模式、守护检查触发器、检索时机调度
4. Agent 层（每 Agent 独立配置模型，可挂 Skills）：Architect、Guardian、Planner、Writer、Judge、Reviser、Consolidator、Branch Manager
5. 记忆与存储层（三层记忆 + 向量 RAG）：L1 正典状态、L2 章节摘要、L3 伏笔台账、卡片库、分支图谱、正文文件、向量索引
6. 外部依赖：LLM API（用户按 Agent 配置）、Embedding API（用户自配）、Skills

## 4. 流水线阶段

### 阶段 0：输入
- 用户提供 brief（世界观 + 主角 + 简介），可选追加资料（材料库，inkos 已有 ingest 能力）

### 阶段 1：设定生成（Architect + Guardian）
- Architect 生成：世界观架构、主线大纲、卷/篇章结构、角色卡（性格 / 口头禅 / 关系 / 成长弧）、地点/势力/物品卡、伏笔清单、节奏曲线、爽点设计、分支图谱初版
- 全部产出可被用户修改（人肉主编可影响世界线）
- Guardian 做一致性审查，将设定卡片化、图谱结构化，写入记忆
- 生成结果默认进入"待确认"，用户可配置为直接写入

### 阶段 2：逐章流水线（每章循环）
1. 守护检查（每章开头）：伏笔铺/收检查、到期伏笔提醒、卡片与状态一致性核对
2. 规划（Planner）：章节意图、节拍设计、目标字数、检索记忆（见第 6 节检索时机 T1/T2）
3. 写作（Writer）：生成正文（默认每章约 4000 字，可配置）
4. 审判（Judge + Reviser）：连续性审计、去 AI 味、节奏/爽点检查；不合格自动重写（循环次数可配置，默认 1~3 轮）
5. 人工审批（Human Gate）：用户阅读 → 通过 / 整章重来 / 局部重启（划范围 + 指令）
6. 整理（Consolidator）：通过后更新三层记忆、卡片、伏笔、分支进度、章节摘要

### 阶段 3：分支管理
- 分支由 AI 生成与更新，用户与 AI 都有权砍分支
- 砍分支 → 受影响章节回滚重写（重新进入逐章流水线）
- 戏份监控：支线角色出场占比超阈值 → 提醒 / 裁剪建议
- 每条分支必须有明确的灰度主线节点（分支汇入主线的位置）

### 阶段 4：导出
- 导出 TXT / Markdown / EPUB（inkos 已有翻译/导出链路可借鉴）
- 平台格式导出（起点、番茄等）列入后续路线图

## 5. Agent 职责与模型配置

| Agent | 职责 | 挂载 Skills |
| --- | --- | --- |
| Architect | 世界观/主线/角色/伏笔/节奏/爽点设计，分支图谱初版 | 可选 |
| Guardian（守护） | 伏笔铺/收检查、卡片一致性、戏份监控、规则守护；唯一可改卡片的 AI | 可选 |
| Planner | 章节意图、节拍、字数规划 | 可选 |
| Writer | 章节正文写作 | 去 AI 味相关 skill 可选 |
| Judge（审判） | 连续性审计、AI 味检测、节奏评分 | 去 AI 味 skill |
| Reviser | 按审计意见重写 | 去 AI 味 skill |
| Consolidator | 更新记忆/卡片/伏笔/分支进度/章节摘要 | 无 |
| Branch Manager | 分支生成、更新、合并建议、砍分支影响评估 | 可选 |

- 每个 Agent 可独立配置：service / model / baseURL / apiKey / temperature / 上下文长度
- 配置保存在用户设置页，读写 inkos 现有 provider 体系（已支持 30+ 服务商 + 自定义 OpenAI-compatible）

## 6. 记忆与检索（三层 + RAG）

### 6.1 三层记忆
- L1 结构化正典状态（每章更新）：当前冲突、当前目标、主角状态、当前位置、敌我关系、known truths（inkos 已有 current_state + facts）
- L2 章节摘要（每章一条）：角色、事件、状态变化、伏笔活动、章节类型（inkos 已有 chapter_summaries）
- L3 长期台账：伏笔 ledger（含依赖 / 半衰期 / 促销标记，inkos 已有 hooks）、卡片库、分支图谱、卷摘要

### 6.2 向量库（新增）
- 内容源与分块颗粒度：
  - 正文：每章 1 个 chunk（正文 + 该章摘要）
  - 卷摘要：每卷 1 个 chunk
  - 设定：每张卡片 1 个 chunk
  - 分支图谱：每节点 1 个 chunk
- embedding 由用户配置（OpenAI-compatible `/v1/embeddings`，例如硅基流动 BAAI/bge-m3 等免费模型），配置项：baseURL、model、apiKey、向量维度
- 检索 top-k 默认：卷摘要 2、章节摘要 6、正文 4、卡片 6（均可配置）
- 写入时机：章节通过后由 Consolidator 写入/更新

### 6.3 检索时机设计（颗粒度）
| 时机 | 触发点 | 查询输入 | 检索范围 | 目的 |
| --- | --- | --- | --- | --- |
| T1 章前规划 | Planner 生成章节意图前 | 当前主线节点 + 目标 + 大纲节点 | 卷摘要 + 近 N 章摘要 + 相关卡片 + 未回收伏笔 | 让规划接得上全局 |
| T2 写作前 | Writer 动笔前 | 章节意图 + 大纲节点 | 最近正文 chunk + 角色/地点卡 + 相关伏笔 | 细节一致、伏笔到位 |
| T3 伏笔检查 | Guardian 每章开头 | 当前章节号 + 主线节点 | 未回收 / 到期伏笔 + 分支节点 | 铺/收检查 |
| T4 审判 | Judge 审计时 | 本章正文 | 相关历史正文 + 设定卡 | 连续性核对、去 AI 味 |
| T5 分支操作 | 新建 / 砍分支时 | 分支描述 | 关联节点 + 受影响章节 | 影响评估与回滚范围 |

### 6.4 自动降级
- embedding 未配置或调用失败 → 自动降级为关键词检索（inkos 现有 scoring 逻辑），不阻塞流水线
- 降级在设置页可见，可手动切回

## 7. 分支图谱

- 结构：主线 1 条（mainline 节点链）+ 分支 ≤ N 条（N 可配置），每条分支末端必须是灰度主线节点（gray node，即分支汇入主线处）
- 生成与更新：Branch Manager（AI）生成、更新；用户与 AI 都有权砍分支
- 砍分支：标记分支为 cut → 列出受影响章节 → 回滚重写（重新进入逐章流水线）
- 戏份监控：统计各分支角色出场占比，支线超主角 → 守护 Agent 提醒 + 裁剪建议
- 可视化：Studio 新增"分支图谱视图"（基于 ReactFlow，复用 inkos 已有的 FlowView 模式）

## 8. 卡片系统

- 卡片类型：角色卡、地点卡、势力卡、物品卡（后续可扩展）
- 卡片内容示例（角色卡）：姓名、身份、性格、口头禅、与主角关系、目标、成长弧、当前状态、出场章节区间
- 权限：仅守护 Agent 与用户可修改；写作/审判 Agent 只读
- 展示：Studio 卡片视图，美观卡片墙（改版 UI 的重点之一）
- 一致性：守护 Agent 定期核对卡片与正文事实

## 9. 人工审批与写入模式

- 审批状态机（每章）：
  draft → ai_reviewed → human_pending → approved → committed
                             ↘ rejected_whole（整章重来）
                             ↘ rejected_partial（局部重启）
- 局部重启：用户在正文中选择范围 + 写入修改描述 → 生成"局部重启任务"（范围 + 指令引用给 Writer/Reviser）→ Agent 从全局视角重写但聚焦该段落 → 再次进入审判与人工审批
- 写入模式（全局配置，按用户选择）：
  - 直接写入：AI 产出即写入正典
  - 点头生效：AI 产出进入待确认，用户确认后才写入（可细化到设定 / 大纲 / 卡片 / 章节各开关）
- 审批面板：阅读正文、查看审判报告、通过 / 整章重来 / 局部重启、留言给 Agent

## 10. 与 InkOS 复用 / 改造 / 新增映射

### 直接复用
- Architect / Planner / Writer / Continuity（审计）/ Reviser / Consolidator 的提示词与流程
- memory-db（SQLite）、state-bootstrap / state-reducer / state-projections（三层记忆主体）
- materials ingest / retrieve（材料库，关键词检索）
- Studio UI 骨架、ReactFlow FlowView、provider 配置体系（30+ 服务商 + 自定义 endpoint）
- chapter-review-cycle（AI 审计 + 重写循环，作为审判环节基底）

### 改造
- chapter-review-cycle：审计通过后追加"人工审批门"，状态机扩展为 draft → ai_reviewed → human_pending → approved / rejected
- 检索链路（memory-retrieval）：加入向量检索，失败自动降级关键词
- 状态 reducer / 台账：加入分支进度、戏份统计、卡片版本
- 章节删除/回滚（state/chapter-delete）：支撑砍分支回滚与整章重来
- 设定编辑链路：Architect 产出 → 用户可编辑 → 锁定基线

### 新增
- Guardian（守护）Agent：伏笔铺/收检查、卡片守护、戏份监控、规则守护
- 分支图谱模型 + Branch Manager Agent + 图谱可视化视图 + 戏份仪表
- 卡片系统（schema + 存储 + 权限 + 卡片墙 UI）
- 向量 RAG（embedding provider 配置 + 分块 + 检索 + 降级）
- 人工审批 API + 审批面板（通过 / 整章重来 / 局部重启）
- 局部重启任务（范围 + 指令 → 全局视角重写）
- 写入模式（直接写入 / 点头生效）
- 每 Agent 独立模型配置 UI

```
BranchGraph {
  nodes: [{ id, type: mainline|branch|gray, title, desc, chapterRange }]
  edges: [{ from, to, kind: parent|merge }]
  screenTime: { characterId, ratio }        // 戏份统计
  status: active | cut

Card {
  id, type: character|location|faction|item
  fields: {...}, version, owner: guardian|user, lock: bool
}

ChapterApproval {
  chapterNo, state: draft|ai_reviewed|human_pending|approved|rejected_whole|rejected_partial
  judgeReport, humanComment, partialRange?, partialInstruction?
}

WriteMode { setting: auto | approve, perCategory: {setting, outline, cards, chapters} }
```

## 14. 开放问题（可后续细化）

- 分支数量 N 的默认值（建议 3~5，可配置）
- 审判循环轮数默认值（建议 1~3）
- chunk 大小与 top-k 默认值（见 6.2，可配置）
- 戏份监控阈值默认值（建议支线占比 30% 提醒 / 40% 告警）
- 卡片字段模板是否按题材（玄幻 / 都市 / 科幻）差异化
